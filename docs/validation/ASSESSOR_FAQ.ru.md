## A. Валидация и тестовые примеры

### 1. Чем подтверждено, что программа выполняет расчёт правильно?

На трёх уровнях. (1) **OQ — автоматические тесты:** `npm test` запускается в CI при каждом push и PR (`.github/workflows/test.yml`); примеры из источников `tests/cases/**.json` (90 verified, 2 unverified) — через `tests/run-cases.test.js`; 9 эталонных точек Excel и 10-й тест (интервал MC). (2) **Отчёт:** `scripts/validation-report.js` формирует из результатов тестов `validation-report.html` и `.json` (CI artifact; на сайте — папка `validation/`). (3) **PQ** — параллельный расчёт лаборатории по её собственной методике ([PQ_PROTOCOL_TEMPLATE.md](PQ_PROTOCOL_TEMPLATE.md)); платформа не выполняет его вместо лаборатории. План — [VALIDATION_PLAN.md](VALIDATION_PLAN.md) §4–5.

### 2. Какое требование каким кодом и тестом покрыто?

Требования — в `docs/validation/REQUIREMENTS.md` (ID: `REQ-<SOHA>-NNN`), карта «требование → код → тест» — в `rtm.map.json`; `scripts/rtm.js` формирует из них [RTM.md](RTM.md). Требование, не связанное с кодом или тестом, роняет `npm test` (`tests/validation/rtm.test.js`). Подробная матрица, ведущаяся с P01, — `docs/VALIDATION_MATRIX.md` (обозначения состояния: verified / известное расхождение / pending / unverified).

### 3. Откуда взяты формулы?

Над каждой формулой и правилом в коде есть комментарий с источником (например, `src/engine/evaluate.js`: "Welch–Satterthwaite … Ref: JCGM 100:2008 G.4.1 Eq. (G.2b), G.4.2"). Источники — в `docs/references/`: JCGM 100:2008, JCGM 101:2008, JCGM 102:2011, JCGM 106:2012, EA-4/02 M:2022, ILAC P14:09/2020, ILAC G8:09/2019, ILAC P10:07/2020, ILAC G24 / OIML D 10:2022, EURACHEM/CITAC QUAM:2012, UfS:2019, AQA:2021, Nordtest TR 537 ed. 4, разделы NIST/SEMATECH e-Handbook. Код, опирающийся на документ, которого нет в репозитории, помечен «(unverified)» — перечень: KL-001…KL-006.

### 4. Откуда взяты ожидаемые значения тестовых примеров?

Только из первоисточника: документ из `docs/references/` (со ссылкой на страницу / таблицу) либо лабораторный Excel и руководства из `tests/fixtures/` (со ссылкой на ячейку / цитатой). `tests/fixture-refs.test.js` каждый раз заново читает ожидаемое значение из ячейки Excel или цитаты `.docx` и сравнивает — чтобы исключить ошибку ручного переноса. Числа из отчёта внешнего аудита (`docs/audit/gemini-audit-2026-11.md`) в качестве тестовых значений **не использованы**; их сравнение с источником — раздел C в `tests/cases/DISCREPANCIES.md`. Правило — [CHANGE_CONTROL.md](CHANGE_CONTROL.md) §5.

### 5. Что делается, если обнаружено расхождение с источником?

Расхождение записывается в `tests/cases/DISCREPANCIES.md` с ID (D-01…D-22) и относится к одной из трёх категорий: ошибка движка (исправляется — например, D-01 нормальный квантиль, D-07 численная производная), нюанс источника (например, D-11 — одна ячейка в GUM Table G.2, D-21 — опечатка в JCGM 102) либо соглашение, требующее решения владельца (Q-1…Q-8). Сейчас в состоянии todo два: D-03 и D-05 (KL-010, KL-011) — оба не меняют округлённый результат. Допуск не расширяется «чтобы тест прошёл»; причина в каждом примере указана в `tolerance.*.reason`.

### 6. Каково соответствие эталонным файлам Excel?

9 точек: плотность 1 (`excel-density`), газоанализатор 3 (`excel-gas-p1…p3`), термометр 5 (`excel-term-p1…p5`) — `tests/cases/excel/`. Округлённый вид (y ± U) во всех точках совпадает с содержимым ячейки Excel (`tests/engine/rounding.test.js`: "9 ta Excel nuqtasining ko'rinishi" — «вид 9 точек Excel»). В необработанных значениях есть известные расхождения: при большом ν_eff Excel переходит на нормальный квантиль, движок всегда использует t(⌊ν_eff⌋) (решение владельца Q-1(a); D-02, KL-012). Наблюдения термометра — учебный образец, а не реальные лабораторные данные (`tests/fixtures/README.md`).

### 7. Проводилось ли сравнение с независимыми программами?

Частично. Квантили проверены по таблице независимого расчёта (mpmath) (`tests/engine/quantiles.test.js`, `tests/tools/gen-t-quantiles.py`). Для перекрёстной проверки с **NIST Uncertainty Machine** готовы входные данные 5 примеров (`tests/crosscheck/num/`), но результаты ещё не получены — состояние `pending` (KL-170). **PTB TraCIM** — не реализовано, запланировано (KL-171).

## B. Расчёт: формулы, округление, k

### 8. Не накапливается ли ошибка округления в промежуточных вычислениях?

Движок (`src/engine/`) ничего не округляет — все промежуточные значения хранятся с полной точностью. Округление — только на уровне отчёта: `src/report/rounding.js::roundResult`. Округлённый текст в сохранённых старых результатах не учитывается — отчёт каждый раз округляет заново. При экспорте числа не округляются (`docs/RISKS.md`, итог P05b, R-04).

### 9. Как округляется результат?

Решения, принятые владельцем (`CLAUDE.md`): U — не более 2 значащих цифр (ILAC P14:09/2020 §5), после округления вверх их также остаётся 2: 0,0999 → 0,10 (а не 0,100); y — до последнего разряда U, round half away from zero (как Excel `ROUND`): −0,125 → −0,13. Код: `src/report/rounding.js::roundHalfAway`, `roundUpAway`, `roundResult`; тесты: `tests/engine/rounding.test.js` (для каждого из двух решений отдельный тест).

### 10. Как определяется k, если ν_eff получается дробным?

Правило по умолчанию — `floor`: k = t_P(⌊ν_eff⌋), без ограничения (и при большом ν_eff нет «скачка» к нормальному распределению); при ν = ∞ — точный нормальный квантиль. `interpolate` — необязательная настройка лаборатории. Применённое правило указывается в отчёте (Ref: JCGM 100:2008 G.4.1 Note 1). Код: `src/engine/coverage.js::coverageFactor` (`DEFAULT_NU_RULE = 'floor'`), квантили — `src/engine/special.js`; тест: `tests/engine/quantiles.test.js` (в том числе JCGM 100 Table G.2 и непрерывность / монотонность). Решение владельца — `tests/cases/DISCREPANCIES.md` Q-1.

### 11. Как вычисляются коэффициенты чувствительности? Не даёт ли это ошибку в нелинейной модели?

c_i — символьная производная формулы (`src/engine/sensitivity.js::sensitivities`); численная производная — только резерв и перекрёстная проверка. c = 0 или NaN не поглощается молча — выдаётся замечание `c_zero` / `c_nan`. Члены 2-го порядка (JCGM 100:2008 §5.1.2 Note) вычисляются (`secondOrderTerms`) — по умолчанию как диагностика, с предупреждением `nonlinear`; тест: `tests/engine/second-order.test.js`, `jcgm100-h1-2nd` (GUM H.1.7). Ограничение: члены 2-го порядка справедливы только для нормальных некоррелированных входных величин (KL-014). Для независимой проверки есть Монте-Карло (вопросы 18–19).

### 12. Не перепутаются ли единицы?

Есть анализ размерностей и преобразование единиц: `src/engine/units.js::analyzeDimensions`, `convert`; правило линтера X6 (`src/engine/linter/rules/x06-units.js`); тест: `tests/engine/units.test.js`. Ограничения: поля UI для ввода единиц входных величин нет — единицы задаются через шаблон или API (KL-015); источника (JCGM GUM-6) в репозитории нет — эта часть unverified (KL-002).

### 13. Выявляет ли программа методологические ошибки пользователя?

Для типичных ошибок есть линтер: `src/engine/linter/` (каждое правило — отдельный модуль: X1–X12, A1–A4, M1–M4, D1, L1–L2, MV1–MV2), результат — в `result.findings`; правила и их источники — `docs/LINTER_RULES.md`; тесты: `tests/engine/linter.test.js` (для каждого правила положительный и отрицательный случай). Пороги не являются нормативным требованием — это решения проекта, подтверждённые владельцем (`docs/LINTER_RULES.md` §4; KL-110); отдельные правила — эвристика, опирающаяся на название источника (KL-112). Линтер не гарантирует правильность модели.

## C. Защитные правила: MPE, U = 0, CMC, правило принятия решения

### 14. Не попадёт ли MPE (пределы допускаемой погрешности) калибруемого прибора в бюджет неопределённости?

Программа никогда не делает MPE источником неопределённости автоматически (`CLAUDE.md`, метрологические правила): MPE используется только при оценке соответствия. Если пользователь вручную вводит его как источник типа B, линтер X1 предупреждает (`src/engine/linter/rules/x01-mpe-in-budget.js`, код `x1_mpe_in_budget`; тест `tests/engine/linter.test.js`). `limit` (MPE / допуск) в реестре эталонов служит только для рекомендации интервала между калибровками — в качестве источника не предлагается.

### 15. Не попадёт ли в сертификат результат с U = 0 или U < CMC?

Без предупреждения не попадёт. `zero_u` и `below_cmc` — замечания уровня `error` (`src/engine/linter/rules/x08-zero-uncertainty.js`; `below_cmc` — ILAC P14:09/2020 §5.5). При наличии непринятого `error` отчёт выходит с отметкой «НЕОФИЦИАЛЬНО»; при настройке лаборатории `criticalMode: 'block'` отчёт не выходит вообще (`src/report/sections.js`). Все замечания выводятся и в печатном отчёте — параметра, который бы их скрывал, нет (`tests/ui/findings.test.js`). **Программа не заменяет U на CMC** — решение за лабораторией. Таблица CMC: `src/engine/lab/cmc.js::cmcAt` (`tests/engine/lab.test.js`).

### 16. Можно ли проигнорировать предупреждение?

Только с обоснованием. Замечание уровня warning / error принимается с комментарием не короче 10 символов; принятие записывается в цепочку аудита (роль, время, ID замечания, комментарий; персональные данные не записываются): `src/storage/acceptance.js::acceptFinding`, `MIN_COMMENT`; тест `tests/storage/acceptance.test.js`. Принятое замечание также видно в отчёте.

### 17. Как выдаётся заключение о соответствии? Есть ли правило принятия решения?

`src/engine/decision.js::decide` → `result.decision`: простая приёмка, защитная полоса w = r·U, TUR = T / (2U), вероятность соответствия p_c (нормальное распределение), односторонние / двусторонние пределы, бинарное / небинарное заключение (JCGM 106:2012 §7–8, ILAC G8:09/2019); тест: `tests/engine/decision.test.js` (примеры со ссылками на страницы). **Если правило принятия решения или предел не указаны, заключение не выдаётся**; правило из настройки лаборатории или из шаблона заранее подставляется в окно выбора, но не применяется, пока пользователь его не подтвердит (`decisionPreset`). Если не указан тип модели (`settings.modelKind`), заключения также нет — программа не предполагает, что |y| является погрешностью. Ограничения: KL-111, KL-114.

## D. Монте-Карло и браузеры

### 18. С каким генератором работает Монте-Карло?

Расширенный Wichmann–Hill (JCGM 101:2008 C.3.3): `src/engine/mc/rng.js` (`RNG_DEFAULT = 'wichmann-hill-2006'`); распределения по JCGM 101 §6.4 — `src/engine/mc/distributions.js`; адаптивная процедура §7.9.4 и проверка GUM по §8 — `src/engine/montecarlo.js::monteCarlo`. Тесты: `tests/engine/mc-rng.test.js` (константы Table C.2, равенство с точной арифметикой), `mc-distributions.test.js`, `montecarlo.test.js`; примеры из источника — JCGM 101 §9.2–9.5 (`tests/cases/jcgm101/`). По качеству генератора TestU01 BigCrush не проводился — принято утверждение источника (KL-023).

### 19. Воспроизводится ли результат Монте-Карло?

Да — начальное значение (seed) задано явно: по умолчанию 20261110 (`MC_SEED`), его можно изменить; имя генератора, начальное значение, M и достигнутый допуск записываются в результате (`rng: { name, seed }`, `M`) и в отчёте. В одной и той же среде одинаковые начальное значение и M дают побитово одинаковый результат (`tests/engine/mc-rng.test.js`: зафиксированные значения). Старые результаты ENGINE ≤ 2.5.0 в точности воспроизводятся с `rng: 'xorshift32-legacy'` (`tests/engine/mc-legacy.test.js`). Разные браузеры — следующий вопрос.

### 20. Одинаков ли результат в разных браузерах?

Последовательность R(0, 1) везде побитово одинакова (только арифметика IEEE 754). Но `Math.log` / `sin` / `cos` в разных JS-движках могут различаться в последнем двоичном разряде, поэтому **необработанные** значения MCM с гауссовыми входными величинами различаются относительно на ≈ 10⁻¹⁶ (`docs/RISKS.md` R-24, измерение 2026-11-18). Решение владельца B (2026-11-19): в необработанных значениях принимается относительное расхождение ≤ 1·10⁻¹⁴; **округлённые y, U, k и границы интервала в отчёте обязаны совпадать в точности**; собственная копия log / sin / cos в движок не добавляется. Проверка: `tests/crossbrowser/` (Playwright — Chromium, Firefox, WebKit; отдельный job в CI); измеренное расхождение — в отчёте о валидации. **Фактическое измерение (Node 22.23 ↔ Chromium 157, 2026-11-19):** 91 пример, из 28 807 чисел различаются 242; округлённое расхождение — 0; 14 плохо обусловленных производных значений (в 4 примерах JCGM 102: наименьшее собственное значение почти сингулярной ковариационной матрицы и k_p, близкая к нулю корреляция, проверка численной производной) превышают 1·10⁻¹⁴ (макс. 3,4·10⁻¹¹) — они внесены в явный список исключений (`tests/crossbrowser/exceptions.json`), по остальным макс. 9,8·10⁻¹⁵. Список исключений ожидает подтверждения владельца (`docs/RISKS.md` R-27 (1)). Измерения для Firefox и WebKit — в разделе 4 отчёта о валидации. Safari (macOS / iOS) автоматически не проверяется — это делает лаборатория в PQ (KL-150…KL-152).

### 21. Будет ли известно, в каком браузере выполнен расчёт?

Да. В документ расчёта (`uc-calc/1`) и в печатный отчёт записываются среда, в которой выполнен расчёт, — краткое имя и версия браузера — и build (`src/io/env.js::describeEnvironment`). Полная строка userAgent не сохраняется (минимизация); эти сведения в Firebase не записываются.

## E. Версия, изменения, воспроизведение

### 22. Не изменится ли результат расчёта незаметно при обновлении программы?

Любое изменение, влияющее на расчёт, повышает `ENGINE_VERSION` (`src/engine/version.js`) и записывается в `CHANGELOG.md` с указанием «влияния на результат». Есть тест, контролирующий это механически: SHA-256-хеш файлов `src/engine/` и `src/report/` сравнивается с `tests/security/engine.sha256.json` (`tests/security/static.test.js`; `tests/tools/engine-hash.js`) — если код изменён, а хеш не обновлён, `npm test` падает. В каждой версии результаты `tests/cases/` побитово сравниваются с предыдущей версией (`scripts/cases-snapshot.js`). Полный порядок — [CHANGE_CONTROL.md](CHANGE_CONTROL.md). Обновлением сайта лаборатория не управляет; решение о повторении PQ в новой версии — за лабораторией.

### 23. Как узнать, какая именно версия работает на сайте?

Deploy — через GitHub Actions (`scripts/build-site.js`, `.github/workflows/deploy.yml`): на сайте есть `build.json` (`commit`, `shortSha`, `engineVersion`, `engineHash`, `builtAt`, `node`), в каждой ссылке на модуль — `?v=<shortSha>`. В нижней части печатного отчёта выводятся название программы, `ENGINE_VERSION`, build, шаблон, ID / дата расчёта, хеш и QR (`src/report/footer.js::footerModel`). При выходе новой версии в браузере появляется баннер (страница автоматически не перезагружается). Шаг настройки, который выполняет владелец, — `docs/DEPLOY.md` (KL-160): пока источник Pages не переведён на «GitHub Actions», сайт публикуется из branch без шага сборки — `build.json` нет, в отчёте вместо build показывается хеш движка с отметкой «dev».

### 24. Можно ли восстановить и проверить старый расчёт?

Да. Расчёт экспортируется в документ `uc-calc/1`: входные данные, результат, замечания, ID / версия шаблона, `ENGINE_VERSION` и канонический хеш (RFC 8785 JCS + SHA-256) — `src/io/calc-json.js::buildCalcDoc`, `src/storage/canonical.js::jcsHash`. При импорте хеш проверяется (изменённый файл отклоняется), а результат пересчитывается и сравнивается (`reproduce`). Тест: `tests/io/calc-json.test.js` — на всех примерах из источников экспорт → импорт → повторный расчёт побитово одинаков. Хеш и QR в печатном отчёте относятся к этому документу. Ограничения: хеш не охватывает реквизиты документа (KL-117); результат MCM в другом браузере может отличаться в необработанном значении (KL-150); открытая страница `/verify` — не реализовано (KL-120, P15).

### 25. Может ли сотрудник случайно изменить формулу утверждённой методики?

Состояния шаблона: DRAFT → REVIEWED → APPROVED → RETIRED (`src/templates/interpreter.js::transition`). В шаблоне APPROVED блокируются модель, выходные величины, варианты, константы, входные величины, источники типа B, корреляции и измеряемая величина (`DEFAULT_LOCKED`, `lockedSections`); тесты — `tests/templates/`. Каждый расчёт сохраняется с ID и версией шаблона. Ограничения: все встроенные шаблоны сейчас DRAFT — перевод в APPROVED является задачей лаборатории (`docs/templates/APPROVAL_CHECKLIST.md`; KL-123); шаблоны режимов BETA не могут стать APPROVED; в локальном режиме защита по ролям — на уровне предупреждения (KL-086, KL-132).

### 26. Если запись исправлена, видны ли первоначальное значение и тот, кто исправил?

На уровне хранения (IndexedDB) каждое сохранение и удаление добавляет append-only запись аудита: порядковый номер, время, актор (роль), действие, прежнее и новое значение, причина, хеш предыдущей записи (`src/storage/audit.js::makeEntry`, `verifyChain`). Тест: `tests/storage/storage.test.js` — изменение или удаление записи обнаруживается. **Ограничения:** аудит находится в браузере пользователя — он *обнаруживает* нарушение, но не предотвращает его (KL-131); в поле актора для записей реестра, принятия замечаний и P12 записывается не имя человека, а роль (`cleanRole`); в редакторе шаблонов же записывается значение, введённое самим пользователем (`src/ui/tpl/app.js::persist` — свободное текстовое поле с названием «Кто (логин или роль, не ФИО)»: технически программа не ограничивает ввод имени; запись остаётся только в IndexedDB этого браузера, в Firebase не отправляется — `docs/RISKS.md` R-27 (6)); состояние текущей сессии пока в `localStorage` (KL-130); состояния режимов регрессии / top-down / специальных режимов — без следа аудита (KL-055, KL-064, KL-076). Неизменяемый аудит на стороне сервера — запланировано (P15, KL-173).

## F. Данные и права доступа

### 27. Где хранятся данные? Пропадут ли они при очистке браузера?

Расчёты, шаблоны, реестр, данные QC, PT и валидации хранятся в браузере пользователя (IndexedDB — `src/storage/`; отдельные состояния — в `localStorage`). Хранения на сервере и централизованной резервной копии **нет** — при очистке данных браузера неэкспортированные данные теряются. Средство резервного копирования — экспорт: один расчёт (`uc-calc/1`) и полный экспорт / импорт (`src/storage/export.js::exportAll`, `importAll`; тест `tests/storage/storage.test.js`: экспорт → импорт в пустую базу → экспорт побитово одинаков). Старые данные `localStorage` переводятся в новый формат миграцией (`src/storage/migrate.js`). Порядок резервного копирования — ответственность лаборатории; сервер — запланировано (KL-134, KL-173).

### 28. Где находятся персональные данные? Уходят ли данные расчёта наружу?

Данные расчёта на сервер не отправляются: отсутствие сетевых вызовов в `src/io/` проверяется статическим тестом (`tests/io/import.test.js`); данные реестра, QC, PT в Firebase не записываются. Firebase — только для регистрации, организаций и оплаты; какое персональное поле где хранится — `docs/DATA_RESIDENCY.md` §2. Имена лиц в отчёте (заказчик, утверждающий) — только в `sessionStorage`, реквизиты лаборатории — в `localStorage`. Новые персональные поля не добавляются (`CLAUDE.md`). Необходимость переноса данных на сервер в Узбекистане проходит повторную юридическую оценку (KL-144). Остаток: внешний запрос к Google Fonts (KL-142).

### 29. Как управляются права доступа?

Аутентификация — Firebase Authentication; пароли только в Auth, в клиентском коде логина / пароля нет; супер-админ — Auth custom claim. Правила Firestore находятся в репозитории (`firestore.rules`: default deny, чтение по членству) и проверяются тестами в Emulator (`npm run test:rules`, `tests/security/firestore-rules.test.js`); статические проверки — `tests/security/static.test.js` (нет inline-скриптов, CSP `script-src 'self'`), XSS — `tests/security/xss.test.js`, `src/ui/escape.js::escHtml`. Роль в локальных данных: эталон и CMC `employee` редактировать не может (`src/storage/registry.js::canEditRegistry`), в P12 исключение / удаление — admin (`src/storage/quality.js::canQuality`). **Важно:** действия в консоли (развёртывание правил, Auth, claim, миграция) выполняет владелец по `docs/SECURITY_SETUP.md` — их выполнение этим пакетом не подтверждается (KL-140); в локальном режиме защита по ролям — на уровне предупреждения (KL-086).

### 30. Может ли пользователь изменить результат средствами браузера и распечатать поддельный отчёт?

Технически — да: расчёт и отчёт полностью формируются в браузере пользователя, независимого повторного расчёта на стороне сервера нет. Имеющееся средство обнаружения: документ `uc-calc/1` и канонический хеш в нём — при импорте файла результат пересчитывается и сравнивается с хешем / значениями в отчёте (вопрос 24). Повторный расчёт на стороне сервера, утверждение и открытая страница проверки — запланировано (P15, `docs/PLAN.md`; KL-173); электронная подпись — не реализовано (KL-120).

### 31. Контролируются ли внешние библиотеки?

Фреймворка нет. Внешние библиотеки — только в `vendor/`, с точной версией, лицензией и SHA-256 (`vendor/README.md`, `vendor/SHA256SUMS.txt`); скрипты из CDN не загружаются. Тест: `tests/security/vendor.test.js`. Расчётный движок не зависит от внешних библиотек — SheetJS и библиотека QR нужны только для импорта / отчёта и загружаются динамически через `src/io/vendor.js`. Импорт из файла: формулы не выполняются, ограничения объёма — в `src/io/import.js::LIMITS`. Обновление — вручную (KL-121).

## G. Задачи лаборатории и ограничения

### 32. Что должна сделать сама лаборатория?

(1) Записать свои требования и оценить платформу относительно них — [USER_REQUIREMENTS_TEMPLATE.md](USER_REQUIREMENTS_TEMPLATE.md). (2) PQ: сравнить результат платформы с независимым расчётом по своей методике, в своём браузере (если это Safari — обязательно) — [PQ_PROTOCOL_TEMPLATE.md](PQ_PROTOCOL_TEMPLATE.md). (3) Проверить шаблон по своей методике и утвердить его — `docs/templates/APPROVAL_CHECKLIST.md`. (4) Определить правило принятия решения, тип модели, CMC и правило для ν. (5) Вести порядок экспорта / резервного копирования. (6) В новой версии просмотреть `CHANGELOG.md` и решить, нужно ли повторять PQ. Руководство пользователя — `docs/manual/{uz,ru,en}.md`.

### 33. Какие части не проверены или имеют статус BETA?

Единый перечень — [KNOWN_LIMITATIONS.ru.md](KNOWN_LIMITATIONS.ru.md). Основное: режимы микробиологии и медицинской лаборатории — BETA (в результате всегда предупреждение и отметка; KL-070, KL-071); в регрессии — WTLS / GLS / полином / «U — диапазон» (KL-050, KL-051); часть top-down, относящаяся к ISO 21748 (KL-060); формулы и пороги оценок PT, Cochran, LOD / LOQ (KL-090…KL-095); перечень реквизитов отчёта (KL-116). В результате функции unverified и в печатном отчёте выводится отметка (например, `topdown_unverified`, `cochran_unverified`). Решения проекта, ожидающие подтверждения владельца, также находятся в этом перечне («ожидает подтверждения»).

### 34. Как проверены функции, опирающиеся на платные стандарты ISO?

Платные стандарты в репозиторий не помещаются (`docs/references/README.md`). Источник тестов для таких функций: открытые источники (NIST, GTC / MSL), лабораторные примеры, предоставленные владельцем, или независимый ручной расчёт. Пока источник не определён, функция остаётся `unverified`: обязательного теста по источнику нет, только перекрёстная / аналитическая проверка; в результате — отметка; шаблон BETA не может стать APPROVED (`src/templates/interpreter.js`, `tests/engine/special-modes.test.js`). Самого ISO/IEC 17025:2017 в репозитории также нет — все ссылки на него «(unverified)» (KL-001).

### 35. Можно ли утверждать, что программа «валидирована по ISO/IEC 17025»?

Нет — такое утверждение не делается. Имеется: документированная проверка на стороне разработчика (требования, RTM, автоматические тесты, отчёт о валидации, управление изменениями, перечень известных ограничений). Пригодность к использованию в условиях лаборатории лаборатория подтверждает сама с помощью PQ. Текста ISO/IEC 17025:2017 в репозитории нет, поэтому соответствие его пунктам в этом пакете не проверено (KL-001). Независимое (внешнее) рассмотрение — запланировано (KL-174).

## H. AI-помощник

### 36. Есть ли в программе искусственный интеллект? Влияет ли он на результат?

Есть необязательный AI-помощник, по умолчанию **выключен** (`LAB_DEFAULTS.aiEnabled: false`; включает только администратор лаборатории, изменение — в аудиторском следе). Он не вычисляет и не изменяет результат: y, u_c, ν_eff, k, U вычисляет только детерминированное ядро (`src/engine/`); ядро и слой отчёта не знают о коде AI, хеш ядра и `ENGINE_VERSION` в P14 не изменились (`tests/security/static.test.js`, `tests/ui/ai.test.js`). AI предлагает только черновики и текст: черновик шаблона, черновик записи реестра из сертификата, объяснение замечаний, список возможно упущенных источников (без значений). В выключенном состоянии код AI вообще не загружается. Полное описание — `docs/AI_DESIGN.md`.

### 37. Как контролируется AI? Не попадёт ли его ошибка в отчёт?

- **Подтверждение человеком:** каждое предложение подтверждается отдельно; кнопки «подтвердить всё» нет (для точек калибровки — построчно). Неподтверждённое значение не попадает в шаблон, реестр и расчёт (`src/ai/response.js::applyNumbers`, `certificateToCalibration`).
- **Против выдуманных чисел:** каждое число от AI приходит с цитатой из источника; программа проверяет, что цитата дословно есть во входном тексте и что число встречается в этой цитате — иначе значение отклоняется (`evidenceProblem`; `tests/ai/response.test.js`). Для значений, прочитанных с изображения, этой проверки нет — в окне предупреждение (KL-177).
- **Недоверенный ответ:** ответ проверяется как строгий JSON и по схеме; лишнее поле, HTML / скрипт, несогласованная единица, предложение взять MPE калибруемого прибора в качестве источника — отклоняются.
- **Отметки:** шаблон, составленный по черновику AI, находится в состоянии `AI_DRAFT`; отчёт расчёта по нему выходит с водяным знаком «НЕОФИЦИАЛЬНО». Перевод в `DRAFT` — с комментарием метролога (≥ 10 символов). Комментарий AI на экране — с отметкой «Комментарий AI — неофициально»; в печатный отчёт — только по выбору пользователя, отдельным внутренним приложением. Официальный текст сертификата / протокола из AI не берётся.
- **Аудит:** каждое действие AI (подготовка, копирование / отправка, ответ, каждое подтверждение / отклонение) — в аудиторской цепочке: роль, режим, модель, версия запроса, SHA-256 отправленного текста и ответа (`src/storage/ai.js::aiAudit`). Сам текст в аудит не пишется.

### 38. Какие данные отправляются AI? Не уйдут ли результаты измерений и данные заказчика?

Только структура, по списку разрешённого: формула модели, обозначения и единицы величин, виды источников и распределений, коды замечаний линтера, порядок вкладов (без чисел). Значения измерений, результаты, полуширины, заказчик, имена людей, реквизиты лаборатории, номера сертификата и аккредитации, идентификатор расчёта не отправляются; в отправляемом объекте не может быть значения числового типа (`src/ai/payload.js::assertAllowed`). Это проверено на всех примерах из источников (включая 9 эталонных точек) и на «канареечных» значениях (`tests/ai/payload.test.js`). Исключение — текст методики или сертификата, загруженный самим пользователем: он отправляется только с отдельной отметкой согласия и может содержать имена людей (KL-176). Перед отправкой полный текст всегда показывается.

### 39. К какому сервису подключается AI? Где хранится ключ?

Два режима. **Копирование** (основной): программа не выходит в сеть — пользователь копирует текст в выбранный им AI и возвращает ответ. **Свой ключ** (необязательный): отдельная страница `ai.html` обращается к `api.anthropic.com` с собственным ключом Anthropic API пользователя; разрешение на этот адрес есть только в CSP этой страницы, CSP основных страниц не изменён (`tests/security/ai-csp.test.js`). Ключ хранится только в `sessionStorage` этой вкладки и стирается при её закрытии; в постоянное хранилище, IndexedDB, экспорт и аудит не пишется (`tests/ai/key.test.js`). В этом режиме данные уходят в зарубежный сервис — на странице есть предупреждение; юридическая оценка — на стороне лаборатории (KL-175). Автоматического теста с реальным сервисом нет — только mock (KL-182).
